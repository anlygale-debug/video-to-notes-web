## 1. 用户与项目目标

用户煜博希望把现有本地视频转笔记工具，从“只会给自己做工具”继续推进成别人也能使用的完整产品。

原始工作流：

1. 输入小红书、B站或 YouTube 视频链接。
2. 解析视频链接和元信息。
3. 下载视频并提取音频。
4. Whisper 转录文本。
5. 调用 LLM 生成结构化 Markdown 笔记。

当前分支正在把一体化流程拆成两个既独立、又能衔接的功能：

- **视频解析器**：解析链接，展示视频信息，下载视频、音频和逐字稿。
- **自适应笔记生成器**：接收逐字稿，先理解内容和用户意图，再生成符合本次需求的笔记。

## 2. 当前代码事实

- FastAPI 单文件后端：`app.py`。
- 当前根路由 `/` 返回 `static/parser.html`，是独立视频解析器。
- 旧版完整笔记页面仍保留在 `/v1`，对应 `static/index.html`。
- `/api/process` 支持 `stop_at: "transcribe"`，视频解析器在转录完成后停止，不继续生成笔记。
- 后端旧笔记生成逻辑仍存在，包括 standard、detailed、scholar 和 Mermaid。
- 现有解析器支持：
  - 小红书
  - Bilibili
  - YouTube（通常需要代理）
  - 其他平台尝试通过 yt-dlp 解析
- 视频解析结果包括封面、标题、简介、作者、平台、时长和原链接。
- 可以下载视频、音频、`.txt` 逐字稿和 `.md` 逐字稿。
- 浏览器 localStorage 保存最近 30 条解析历史。
- 当前本地服务没有启动。
- 已发现但尚未修复的耦合：`/api/process` 即使使用 `stop_at: "transcribe"`，仍会在流程开始前检查 LLM API 配置。因此产品概念已拆分，后端依赖尚未完全拆分。
- 视频下载按钮会通过接口重新流式下载视频；音频会暂存到 `/tmp/vtn-audio-{task_id}.mp3`。

## 3. 笔记生成器的灵感来源

用户指定的 skill：

`/Users/yubo/.agents/skills/to-notes/SKILL.md`

该 skill 原本用于把腾讯会议课程逐字稿整理成课堂笔记，流程是：

`逐字稿 → 快速预读 → 动态四问 → 全量通读与大纲 → 大纲确认 → 逐章输出 → 完整性验证`

用户大部分内容实际上是单人口播稿，通常没有时间戳和说话人，因此产品不应把时间戳、说话人作为核心前提。

需要保留的是 skill 背后的思想，而不是机械照搬所有细节：

1. AI 先理解原文。
2. AI 再理解用户这次想要什么。
3. 笔记结构、详细程度和执行流程由内容与用户意图共同决定。
4. 原文长度不直接决定笔记详细程度。
5. 长内容可通过后台分块保证完整性。
6. 必要时先确认大纲。

用户特别认可这个能力覆盖以下场景：

- 短视频可以快速概括。
- 短视频也可以深度拆解。
- 长视频可以生成完整详细笔记。
- 长视频也可以只做核心速览。

## 4. 已确认的笔记交互方向

笔记生成器有两个使用层次：

### 快速生成

- AI 预读逐字稿。
- AI 自动给出推荐设置。
- 用户接受推荐，一键得到笔记。
- 即使后台因长文需要分块，也不一定向用户展示大纲确认。

### 自定义生成

保留四个固定决策维度，保证每次不会漏掉关键设置：

1. 笔记结构
2. 详细程度
3. 生成方式
4. 附加模块

每个维度的具体问题、选项和推荐答案由 AI 根据逐字稿动态生成。

最终采用的原则是：

> 固定决策维度 + 动态问题内容 + 明确执行分支。

### 已识别并需要修复的原 skill bug

原 skill 有时即使用户选择“概括式、一次性生成”，仍机械执行“大纲 → 逐章生成”。

根因是问题层和执行层脱节。

新产品必须把两个概念分开：

- **后台分块**：为了长文本处理完整，是内部技术策略。
- **大纲确认**：是否展示大纲、等待用户确认，是交互策略。

执行路径应由明确的产品规则决定，不能完全交给 LLM 自由发挥：

| 用户选择 | 实际流程 |
|---|---|
| 速查摘要 + 一次性生成 | 直接生成，不展示大纲 |
| 要点提炼 + 一次性生成 | 直接生成完整笔记 |
| 完整详解 + 一次性生成 | 后台可分块，最后一次展示 |
| 完整详解 + 大纲确认 | 生成大纲 → 用户确认 → 逐章生成 |
| 用户明确选择先看大纲 | 无论原文长短都先展示大纲 |

### 已确认的视觉语言

- 暖米色／羊皮纸背景
- 像素风大标题
- 正文使用高可读字体
- Meta 信息使用等宽字体
- 粗黑边框
- 无模糊硬阴影
- 方正、模块化卡片
- 蓝色主操作
- 绿色成功
- 红色错误或少量强调
- 标签、编号、版本信息和机械式状态条
- 编辑出版物／像素杂志式排版

### 视觉适配原则

1. 复制视觉气质，不复制原网页内容。
2. 沿用设计语言，不沿用原站架构。
3. 功能逻辑和中文长文本可读性优先。
4. 游戏化世界观文案少量使用，核心操作文案保持直白。
5. 像素字体主要用于标题、数字和标签，不进入长篇笔记正文。
6. 原图优先于视觉包；视觉包负责把原图气质变成可执行规则。
7. 示例 HTML 使用渐变，但严格规范和原图都不支持 UI 渐变；正式实现不照搬渐变。

视觉方向可概括为：

> 中文 AI 知识处理工作台，具有 16-bit 编辑出版物的视觉气质。
